      Arquitetura da solução

      Fluxo implementado com Node.js: o frontend fala apenas com o gateway, que orquestra dois microsserviços independentes.

      FrontendHTML · CSS · JavaScript
      API Gatewayporta 3000 · /api/clima?cidade=…
      Microsserviço de localização (porta 4001) → Open-Meteo Geocoding
      Microsserviço de meteorologia (porta 4002) → Open-Meteo Forecast
      Histórico das últimas 5 cidades (no gateway)

      Contrato do gateway: validar cidade com 2 a 100 caracteres; retornar 400 para entrada inválida, 404 quando não houver localização, 502 para indisponibilidade ou timeout externo e 200 para consulta bem-sucedida. Esta página consome o gateway; só os microsserviços falam com a Open-Meteo.

      EndpointDescriçãoRespostas
      GET /api/clima?cidade=…[&id=…]Localiza a cidade, busca clima atual + previsão de 5 dias e registra no histórico200 · 400 · 404 · 502
      GET /api/historicoÚltimas 5 cidades consultadas200
      GET /api/saudeEstado do gateway e dos dois microsserviços200
      GET :4001/localizar?nome=…Microsserviço de localização (Geocoding)200 · 400 · 404 · 502
      GET :4002/clima?lat=…&lon=…Microsserviço de meteorologia (Forecast)200 · 400 · 502

      Questões para discussão em sala

      1. Qual é a diferença entre consumir uma API diretamente no frontend e consumi-la por meio de um backend?
      2. Por que as consultas meteorológicas utilizam latitude e longitude em vez de apenas o nome da cidade?
      3. Qual é a diferença entre dados meteorológicos atuais e uma previsão?
      4. O que deve acontecer quando a Open-Meteo deixa de responder ou excede o tempo limite?
      5. Quais são as vantagens de separar os serviços de localização e meteorologia?
